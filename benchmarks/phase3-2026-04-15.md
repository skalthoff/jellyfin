# Porcupine Phase 3 Results — 2026-04-15

## Changes Applied (cumulative)
- Phase 1: Indexes on ItemValueMap(ItemId), BaseItem(TopParentId,Type,SortName), UserData(UserId,ItemId)
- Phase 2: AsSplitQuery, filtered UserData Include
- Phase 3: Fully materialized artist query (pre-resolve ItemValueIds → ItemIds, then IN clause)

## Results

| Query | Baseline | Phase 3 | Speedup |
|---|---|---|---|
| Album listing (400) | 19.8ms | 12.5ms | 1.6x |
| Album listing + COUNT | 23.2ms | 14.4ms | 1.6x |
| **Albums by artist** | **32.7ms** | **5.9ms** | **5.5x** |
| **Tracks by artist** | **502.7ms** | **11.7ms** | **43x** |
| Artist listing (400) | 3.0ms | 3.8ms | — |
| Recently played | 230.7ms | 591.3ms | regression |
| Search 'rock' | 119.5ms | 622.0ms | regression |
| Tracks in album | 0.7ms | 0.4ms | 1.7x |

## Key Findings
- Fully materializing the ItemValue→ItemValueMap lookup chain (3 separate queries instead of 1 correlated subquery) produces **43x** improvement on the worst-case artist query
- AsSplitQuery helps simple listing queries but hurts queries with correlated WHERE clauses
- Recently played and Search have separate bottlenecks (UserData join and LIKE scan) that need investigation
- The search regression may be related to additional indexes causing SQLite query planner to choose worse access paths

## Next Steps
- Investigate Recently played regression — may need to revert AsSplitQuery for queries with UserData WHERE clauses
- Investigate Search regression — may need to revert some indexes or use a different search strategy
- Apply the materialized query pattern to JellyfinQueryHelperExtensions.cs
